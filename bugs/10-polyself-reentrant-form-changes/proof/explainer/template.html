NetHack 5.0 · polyself.c · formal verification

How the polymorph proof works

The bug. polymon() installs a new hero form and then spends about 250 lines applying its consequences. Some of those steps can change the form again (a revert when u.mh hits zero, a polymorph trap), and the outer code then carries on for a form that is gone. Bugs 06, 07 and 08 are three results.

The fix (PR #1681) gives every form installation a new generation number, bumped inside set_uasmon(). polymon() and break_armor() save the number and stop at eight checkpoints if it has changed.

The argument has two halves. First, a lemma, proved exhaustively by CBMC and for every input by Frama-C/WP on a small C model: the old operation continues past a checkpoint only if nothing was installed meanwhile, even when a callback reinstalls the same form. Negative controls show every checkpoint is needed and that the checks can fail. Second, three premises connect the model to NetHack, and are checked by source audits and review, not by the provers: every form installation goes through set_uasmon(); every bump inside the window belongs to an installer that finishes its own form's setup; a checkpoint follows every re-entrant call.

Six short parts follow. Each has a live figure (the model runs in your browser), and every boundary links to the NetHack 5.0 source at 16ff59115, with the patch shown as a diff.

    Sources: proof/ (polyself_model.c, polyself_acsl.c, run-cbmc.sh, run-wp.sh, the audits), the bug's REPORT.md, and upstream #1682 / PR #1681. The in-page model is a line-by-line JavaScript transcription of polyself_model.c; it reproduces all 18 expected outcomes in run-cbmc.sh.

    The window · a form change that isn't atomic

    Question: after set_uasmon() installs a new form, what happens if something in the next few hundred lines changes the form again?

    The code for the selected column

    polymon() installs the new form in one line (u.umonnum = mntmp; set_uasmon();), then spends about 250 lines applying what that form implies: armor it can't wear, a weapon it can't hold, being expelled, the square you are standing on, artifacts that now reject you. Several of those steps can hurt you. A polymorphed hero whose u.mh reaches zero is reverted on the spot by rehumanize(), from inside polymon(). Other steps can polymorph you again.

    When the nested call returns, the outer code keeps going as if its form were still installed. Each scenario above is one way that goes wrong.     From NetHack to a model · keep the boundaries, drop everything else

    Question: how do you check a property of 250 lines of game code that call into half the game?

    You don't check the real thing. You write a small C program that keeps only what the property depends on: where the code can re-enter, which form is installed, a generation counter, the light source, and a record of cleanup. Every call that might re-enter becomes a single choice with four outcomes. Click a tagged line on either side to find its counterpart.

    This step is called abstraction. It is where most of the judgment in a proof like this goes. The callbacks (break_armor(), spoteffects(), and the rest) are not modeled at all. Each is replaced by "anything could happen to the form here", which is an over-approximation: the model allows everything the real code can do, and more. If the property holds under every outcome, it holds under whichever outcome NetHack actually produces.

    The price is that the model says nothing about what those callbacks do to anything else. The link between the model and the source has to be argued separately, which is what part 6 does.

    Where this step is in NetHack

    Each boundary asks for one choice, as nondet_uint() does in the C model. The model checks three assertions as it runs:

    • apply_owned_effect(): the old transformation never applies a stale-form effect. If the code continues past a boundary, the generation must be the one it saved.
    • cleanup_current_form(): cleanup runs at most once for each form generation (bug 06).
    • assert_light_consistent(): form and hero light source agree (bug 07).

    Try the presets. With no guard, any revert fails the first assertion (the shape of bugs 06 and 08). The identity guard catches a revert, but not a same-form reinstall at retouch_equipment. The generation guard catches both. Keep a set of choices and switch guards to compare them on the same path.

    Every path at once · what CBMC does

    Question: is there any choice of callback outcomes that makes the old form apply an effect after it has been replaced?

    function
    guard

    The tree. Each level is a boundary, and each node branches four ways, one per outcome of nondet_uint(): · nothing, @ revert, : another form, y the same form again. A leaf is where a path ends: ● the function completed with every assertion true, ■ a guard returned early, ✕ an assertion failed, or ○ the path was excluded by an __CPROVER_assume. Click a leaf to step through that path against the source. (This page draws a path as ending at its first failure. CBMC would carry on and report each violated property separately.)

    What CBMC actually does. It does not walk this tree. It translates the whole C program into a single SAT formula, one Boolean variable per bit of every value at every point, with nondet_uint() as unconstrained inputs, __CPROVER_assume(c) as a constraint, and the negation of every __CPROVER_assert as the goal. It then asks a SAT solver: is there any assignment of the inputs that reaches a false assertion?

    • No such assignment (unsatisfiable): the property holds on every path. CBMC exits 0.
    • An assignment exists: the solver's answer is a concrete counterexample trace, the same kind of path you can step through here. CBMC exits 10.

    It is "bounded" because loops and recursion have to be unrolled to a fixed depth first. This model has no loops, and --unwinding-assertions makes CBMC confirm that no path was cut off, so here the check is exhaustive. The flags --bounds-check --pointer-check --signed-overflow-check and the rest add C safety assertions on top of the model's own.

    The CBMC harness: verify_polymon_guards() and verify_break_armor_guards()

    Breaking the fix on purpose

    A proof can pass for the wrong reason: an assumption that rules out every interesting path, or an assertion that can never fail. run-cbmc.sh protects against this by running some checks that are supposed to fail. For each one it breaks the fix in a specific way and requires CBMC to find a counterexample (exit 10). This table runs all 18 checks with the in-page model.

    Guard necessity (the last eight rows). For each of the eight guards, the script forces an ordinary revert to human at exactly that boundary (-DFORCE_BOUNDARY=k), removes just that guard (-DOMIT_GUARD=k), and requires a counterexample. This shows that every guard is reachable and needed. A patch with one guard missing is caught, and so is a harness that couldn't reach that boundary.

    The ABA rows. The identity guard passes only when same-form reentry is assumed away (-DALLOW_SAME_FORM_REENTRY=0) and fails without that assumption. That is the result that led to the generation counter. The polymorph-trap route rows use a fixed path that the source audit shows NetHack can actually reach.

    Delayed light bookkeeping reproduces bug 07: in the old code, set_uasmon() installs a glowing form, and a nested rehumanize() sees a glowing form with no light source to delete.

    A→B→A · why a counter, not the form number
    
  
    Question: polymon(y) saved "my form is y". A nested callback runs. Afterwards the form is y. Did anything happen?
    
  
    Add nested installations and watch the two guards. The identity guard compares the form number now to the saved one. The generation guard compares a counter that every installation increments. They disagree whenever the history returns to where it started, which is called the ABA problem in concurrent programming.

    Why ABA matters here. A same-form installation is a real event. The nested polymon() ran its own cleanup, including retouch_equipment(), for its own generation. When the outer call continues, it repeats that work, which is bug 06's double blast even though the form number never changed. The identity guard that PR #1681 first proposed (if (u.umonnum != mntmp) return 1;) cannot see this.
    
    
    The fix (proof/generation-guard.patch, the last commit of PR #1681): a static unsigned long uasmon_generation that note_uasmon_install() increments at the end of set_uasmon(), the function every form installation calls. It is never reset, so a saved value can equal the current one only if nothing was installed in between. Wraparound would break that, so the patch calls panic() if the counter reaches 0 again. The counter is not saved to disk, because a re-entrant call chain cannot span a save and restore.

    What WP adds · a proof for every input, not every path
    
  
    Question: CBMC checked every path of one small program, starting from generation 0, with one installation per callback. Does the lemma hold in general?
    
  
    Frama-C/WP reads C annotated with ACSL contracts (requires, ensures, assigns, assert, loop invariants) and proves each function against its own contract for every input its requires allows. So the result does not depend on a starting state, and a loop with an invariant covers any number of iterations. run-wp.sh checks every function in polyself_acsl.c and fails if any property is left merely assumed.
    
  
    
    
    what WP proveswhere
    
    
    The boundary lemma: after any callback outcome, same-form reinstall included, the owner continues only if nothing was installed.generation_boundary_arbitrary_aba()
    
    
    The same with no limit on installations: a callback may install any number of forms in any order (A→B→A chains of any length), and the owner continues if and only if it installed none. A loop invariant carries "after i installs the generation is exactly i past the start".generation_boundary_any_installs()
    
    
    Every installation keeps the form and its light source in agreement (bug 07), and cleanup never runs twice for one generation (bug 06).install_form(), epoch_boundary(), entry points
    
    
    Runtime safety of the model itself: no overflow of the counter, no out-of-bounds read.-wp-rte
    
  
    
  
    Result: 488 of 488 goals proved (433 by Qed, WP's simplifier; 47 by the Alt-Ergo SMT solver; 8 trivially), and no property left assumed.
    
  
    
    
    The negative control. WP cannot produce a counterexample, but it can fail to prove. run-wp.sh rebuilds the identity-guard model with -DIDENTITY_MAX_CHOICE=3, which allows a callback to reinstall the owner's form, and requires that exactly one goal then stays unproved: the identity boundary's assert choice == 0. Everything else still proves, which pins the failure on ABA and nothing else. (CBMC gives the concrete counterexample path; see part 3.)
    
    
    Why "every function" matters. WP is modular: a caller relies only on its callees' contracts. An earlier run restricted WP to the two top-level entry points (-wp-fct) and reported 76/76, but that assumed the boundary function's contract, which carries the whole lemma, without checking it. Checking every function also exposed a missing precondition in epoch_boundary(), now fixed.

    What the proof rests on · three premises and the audits
    
  
    Question: the provers checked a model. What makes the model a faithful picture of src/polyself.c?
    
  
    Three premises, checked by source audits and review rather than by the provers:
    
  
      
    
    1. Every form installation goes through set_uasmon(), which bumps the counter. audit-form-transitions.mjs lists every write to u.umonnum or gy.youmonst.data and every set_uasmon() call (the table below) and fails if one appears without review. audit-patch.mjs applies the PR's patches and checks the bump is in set_uasmon().
      2. 
    
    2. Every bump inside the window belongs to an installer that finishes its own form's setup: a nested polymon() or rehumanize(). The other set_uasmon() callers are refreshes (set_ulycn() when you eat, quaff, fight or pray; the were-change refresh between turns), game start, or restore, and none can run inside polymon() or break_armor(). This one is checked by review only.
      3. 
    
    3. A checkpoint follows every re-entrant call. The model's eight boundaries come from reading the source; audit-patch.mjs checks all eight generation guards are in the patched code with no identity guard left, and part 3's negative controls show each is needed.
      4. 
  
    
  
    audit-form-transitions.mjs: every direct form write, and why it's accepted
    
  
    
  
    
  
    
  
    
    
    audit-form-transitions.mjs strips comments and string literals from every .c/.h file, matches u.umonnum =, gy.youmonst.data = and set_uasmon(, and compares the result, as a multiset of normalized lines, to the 16 reviewed entries above. It includes a self-test showing that commented-out writes and == comparisons are not counted.
    
    
    audit-callgraph.mjs repeats the form-write scan with the reviewed line numbers hard-coded, checks which files call set_uasmon(), and counts direct polymon( call sites. The manifest records 21. It requires that the list include trap.c (the ABA route) and polyself.c (recursion). It does not review the 21 callers one by one.
    
    
    The last column is premise 2. The audits are drift detectors: they cannot decide what a new site means, only that it is new, and audit-callgraph.mjs pins line numbers, so any upstream edit to those files makes it fail until someone re-reviews.
    
    
    Out of scope by design. What the callbacks do to state other than the form, its light and its cleanup; function pointers; and the rest of NetHack. The claim is modular: the re-entrancy protocol is right, and the source matches it at the reviewed sites.
